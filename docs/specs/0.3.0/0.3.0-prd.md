## 0. Overview and Positioning

**0.3.0 is ASCI's first public release (macOS first; Windows depends on EV signing lead-time).** Target deadline 2026-06-19, approximately 2 weeks of coding (server framework work already overlaps 0.2 Week 3).

**Positioning in four statements**:

1. **OPENSCI accounts** — No self-built ASCI accounts; OPENSCI is the sole sign-in entry, with mandatory sign-in.
2. **Configurable capability packs (Codex-style out of the box)** — 2 built-in scenario packs enabled by default, non-disableable, without configuration; users see capabilities on Configuration and adjust system parameters in Settings.
3. **Release readiness** — Updates, crash/behavior telemetry, GDPR MVP compliance, and release prerequisites with lead-time.
4. **Data portability** — Local research data, one-click open-format export, account deletion.

**Scope reduction**: Capability packs / Agent-led philosophy (0.2 §0) narrow in 0.3 to **background architecture + Configuration presentation**, without forcing them into the primary flow (default-page redesign, Proposal mechanism, activation paths removed from 0.3). User-perceived focus is **accounts + release readiness + data portability**, while capability packs continue developing as the underlying paradigm.

**Priority labels** (from north-star): Required (release gate) / Observe (track without blocking) / Deferrable (move to 0.4 if behind) / 0.4 second release.

### Three Data Categories (Determining Storage and Ownership)

| Term | Definition | Storage | Ownership |
|------|------|---------|------|
| **Research Data Asset** | User research outputs: papers / notes / evidence-sets / evidence-refs / citation-relations / reviews, and full text/PDFs | **Local** `~/.asci/` | **Device-level** (one local library, decoupled from accounts) |
| **Behavioral Telemetry** | Structured signals for product improvement (crashes, feature use, 5 self-evolution signal types), sanitized, never research content | **Server** | Current signed-in account |
| **System Foundation Credentials** | Provider API Key / Zotero credentials / MCP server list / proxy | **Local** `~/.asci/` | **Device-level** (shared across accounts, one configuration per machine) |

> Boundary: Behavioral telemetry **never** collects research-asset content (full literature / PDFs / original notes / conversations) or credentials (API Keys / email / usernames / paths containing usernames).

<a id="能力包-vs-skill"></a>

### Capability Pack vs. Skill

| Term | Definition | User Operations in 0.3 |
|------|------|----------------|
| **Capability Package** | Out-of-box task-domain solution (scenario Agent + Skill references + MCP references + UI framework). 2 built-ins: literature search and literature review | **Enabled by default, cannot disable/uninstall/import** (Codex style); editable in-pack preferences (e.g. default model) |
| **Skill** | One capability fragment (SKILL.md + implementation), referenced by packs and independently toggleable | **Enable/disable**; two sources: system built-in / from capability packs |

<a id="opensci-登录"></a>

### OPENSCI Sign-In

| Term | Definition |
|------|------|
| **OPENSCI sign-in** | ASCI's **sole sign-in entry**. OPENSCI is the IdP; ASCI delegates authentication through OAuth/OIDC. ASCI server holds its own user mapping (OPENSCI uid → ASCI user, identity/telemetry attribution only); user **profile (nickname/avatar/institution/discipline) is read from OPENSCI and displayed read-only**. OPENSCI supplies Email/Google/ORCID sign-in methods; ASCI neither builds registration nor applies for its own OAuth clients. |

# Epic 1: Accounts (Mandatory OPENSCI SSO)

## Problem Statement

ASCI 0.1/0.2 is entirely local without accounts. Public release needs identity for behavior attribution/product improvement, future cross-device sync, and unified OPENSCI ecosystem identity. Users do not want another ASCI account and worry mandatory sign-in locks research data in the cloud, unavailable offline/on other devices.

## Solution

Mandatory sign-in through **OPENSCI as sole entry** (OAuth/OIDC delegation), reusing OPENSCI identity without new ASCI accounts. **Research assets remain local (one device-level library)**; accounts identify users only. Cache tokens encrypted locally and explicitly state research data stays local (**no cross-device-sync schedule**), avoiding the expectation gap of signing in yet finding no data on another device.

> ⚠️ Revision (0.4 grill, 2026-06-01): The original 0.4 sync promise is **withdrawn**. No sync in 0.4 and no schedule promised (see [0.4 north-star §6](../../milestones/0.4/north-star.md)). All Epic copy says local-only without a schedule.

## User Stories

1. As a new user, I want OPENSCI sign-in to ASCI for unified identity without another account.
2. As a user, I want first launch to show OPENSCI sign-in and redirect to authorization, then enter the app.
3. As a user, I want read-only OPENSCI profile (nickname/avatar/institution/discipline) to confirm identity without repeated entry.
4. As a user, I want encrypted local tokens so they cannot be recovered after sign-out.
5. As a user, I want automatic token refresh that invalidates old tokens once, avoiding frequent sign-in and leaked old tokens.
6. As a user, I want papers/notes/evidence sets/reviews to remain on this machine after sign-in, with local assets and controllable privacy.
7. As a user, I want welcome/account pages to clearly state local-only data without a sync schedule, explaining expected absence on other devices.
8. As a 0.1/0.2 user, I want my existing papers/notes/evidence sets visible immediately after upgrade and first OPENSCI sign-in, continuing without rebuilding.
9. As a legacy user, I want Zotero/Provider API Key/proxy/MCP configuration unchanged after upgrade, immediately usable for search/reviews/Zotero without reentry.
10. As a user, I want ASCI functionality gated by sign-in for correct behavior attribution and unified accounts.
11. As a multi-account user on one device, I want different OPENSCI accounts to see the same device-local research library for continuity (device-level semantics).
12. As a user, I want to sign out anytime to switch accounts/protect privacy.
13. As an offline user, I want local functions while offline with an unexpired token, avoiding blocks during travel/intranet/no-network use (subject to OPENSCI tokens).
14. As a user, I want clear sign-in/network failure messages and retry access to understand why entry fails.

<a id="关键产品决策"></a>

## Key Product Decisions

- **OPENSCI sole entry**: No ASCI Email/password registration/reset or Google/ORCID OAuth applications; OPENSCI owns these.
- **ASCI server user mapping** (OPENSCI uid → ASCI user) for identity/behavior attribution only, no stored profile (read live from OPENSCI).
- **Mandatory sign-in** before all functionality.
- **One device-level research library**, not account-isolated, aligned with Zotero; accounts identify only; credentials shared per device.
- **No legacy claiming flow**: Local library is the device library, immediately usable after sign-in.
- **Expectation management**: Welcome/account pages state local-only data, **no sync schedule**, avoiding cloud-data assumptions from mandatory sign-in.
- **Dependency**: OPENSCI builds OAuth/OIDC SSO in parallel during 0.3; freeze contract (Epic 7).

|---|------|--------|

| U-A2 | Tokens encrypted locally; unrecoverable from files after sign-out (inherit 0.1 safeStorage) | Required |
| U-A3 | After refresh, old access token invalid (capture returns 401) | Required |
| U-A4 | Legacy 0.1/0.2 upgrade + first OPENSCI sign-in → existing papers/notes/evidence sets visible; Zotero/Provider/proxy/MCP immediately usable without reentry | Required |
| U-A5 | Account tab shows read-only OPENSCI nickname/avatar/institution/discipline | Required |
| U-A6 | Welcome/account pages explicitly state local-only research data (**no sync schedule**) | Required |

# Epic 2: Configurable Capability Packs (Codex-Style Out of the Box + Configuration + Settings Redesign)

## Problem Statement

In 0.2, packs are background concepts barely visible to users; scattered Skill/MCP/pack settings confuse users. Public 0.3 must offer built-in scenarios without configuration, one place to understand ASCI capabilities, and a clear distinction between system parameters and Agent capabilities.

## Solution

Two built-in packs (literature search/review) integrate through A3, **enabled by default without disabling, installation, or configuration** (Codex style). Existing left Configuration hosts the Agent ecosystem: packs **read-only**, Skills **enable/disable management**. Settings narrows to **10 tabs** (profile → Account) for system foundation; Skills/packs leave Settings, eliminating duplicate access.

## User Stories

1. As a user, I want built-in search/review ready without installation/configuration so I can issue tasks directly.
2. As a user, I want a pack overview on left Configuration to understand ASCI capabilities.
3. As a user, I want read-only scenario Agent / referenced Skills / MCPs / UI framework / in-pack preferences to understand composition.
4. As a user, I want editable in-pack preferences (e.g. scenario default model) to customize behavior.
5. As a user, I want all Skills and their sources (system built-in / capability pack) in Configuration to understand fragments.
6. As an advanced user, I want individual Skill toggles to control Agent capabilities.
7. As a user, I want backlinks showing which packs use each Skill to understand relationships.
8. As a user, I want source/enabled filters to locate Skills quickly.
9. As a user, I want 10 clear Settings tabs (Account/General/Models/Zotero/Proxy/MCP/Data Collection/Shortcuts/Archived/About) for system configuration.
10. As a user, I want Skills/packs only in left Configuration, without Settings entries, avoiding split access.
11. As a search user, I want right-side result lists (field labels/sources/citation counts/sorting/filtering) to review outputs.
12. As a review user, I want right-side review body + paragraph provenance with clickable citations to trace evidence.
13. As a legacy user, I want old Settings Configuration contents moved automatically (MCP → MCP tab; Skills/packs → Configuration), for seamless upgrade.
14. As a user, I want independent MCP Settings for shared system infrastructure consumed by multiple packs.

<a id="关键产品决策-1"></a>

## Key Product Decisions

- **Official packs default enabled, non-disableable, without local import/uninstall** (Codex style); remove existing toggles.
- **CP1 rewritten**: 2 packs through 0.2 §3-4 A3 registration (no hardcoding); removing one removes its scenario without crashes. **No Proposal outputs** (removed from 0.3).
- **Configuration**: Packs **read-only**, except editable in-pack preferences; Skills **toggleable**, with two sources (system/pack, no third-party self-install; existing `importSource` workspace sync stays internal rather than exposed as user installation), plus backlinks.
- **10 Settings tabs**: Account (old profile, OPENSCI + sign-out + DO2 export + DO3 delete), General, Models, Zotero, Proxy, MCP, Data Collection, Shortcuts, Archived, About.
- **Manifest-declared UI framework**: Both packs use conversation + right artifacts; search results list for search, review body + paragraph provenance for review (mostly satisfied by 0.2).
- **No duplicate entries**: Skills/packs only on Configuration, absent from Settings.

# Epic 3: Telemetry (Crashes + Behavior + Self-Evolution)

## Problem Statement

Public release needs data to diagnose crashes, understand feature use, and accumulate future Agent-improvement evidence. Researchers value privacy; EU users require GDPR explicit opt-in for nonessential collection. Research content must never be collected.

## Solution

Three layers: **Sentry** crash reports (sanitized), **PostHog** product behavior, **self-evolution endpoint** for 5 structured signal types (separate channel). Regional defaults: EU IP opt-in (off), non-EU opt-out (on). Data Collection has two independent switches + explanation. Never collect research content/credentials.

## User Stories

1. As a product team, I want uncaught exceptions automatically reported to Sentry with stacks to diagnose crashes.
2. As a user, I want reports free of personal information (sanitized email/IP) for privacy.
3. As a user, I want username path segments replaced with placeholders (`/Users/<USER>/`, `C:\Users\<USER>\`) so stacks do not identify me.
4. As a product team, I want search/review-generation/sign-in events in PostHog for usage analysis.
5. As an EU user, I want nonessential collection off until explicit opt-in for GDPR.
6. As a non-EU user, I want default-on collection with anytime opt-out for control.
7. As a user, I want separate PostHog/self-evolution switches and brief explanation (independent channels, no content, anytime off).
8. As a product team, I want 5 self-evolution signal types (task structure, tool use, model choice, errors/exceptions, workspace structure) + implicit feedback (copy/save/cite/discard/votes/retry) through separate backend channels for 0.4 Agent improvements, physically isolated from behavior analytics.
9. As a user, I want no full literature/PDF/original notes/conversations/credentials in self-evolution telemetry for content privacy.
10. As a user, I want disabling self-evolution to stop endpoint events without affecting PostHog (decoupled switches).
11. As an external auditor, I want repository schemas to reveal collectable fields without reading source, verifying minimization.

<a id="关键产品决策-2"></a>

## Key Product Decisions

- **Three layers**: Sanitized Sentry (including T4a path usernames), PostHog behavior, independent self-evolution 5-signal endpoint physically isolated from PostHog.
- **Remove Proposal feedback**: Delete five-action Proposal decision ratios from the original six-category user feedback; retain implicit signals.
- **Regional defaults**: EU IP opt-in/off; non-EU opt-out/on.
- **Data Collection**: Independent PostHog opt-in + self-evolution toggles.
- **Deferrable**: Entire self-evolution telemetry (§3-A) may defer if the 2-week window is tight; Sentry + PostHog remain minimum release-operations baseline.
- **Boundary**: No literature full text/PDF/original notes/conversations/API Key/email/username/username-bearing paths.

<a id="验收标准-2"></a>

## Acceptance Criteria

| # | Acceptance | Priority |
|---|------|--------|
| T-1 | Trigger crash → Sentry stack visible, payload without email/IP, usernames sanitized in paths | Required |
| T-2 | Run search/review/sign-in → corresponding PostHog event stream | Required |
| T-3 | EU IP account sends nothing until enabled; non-EU sends by default and stops when disabled | Required |
| T-4 | Two Data Collection switches decoupled; self-evolution off leaves PostHog unaffected | Required |
| T-5 | Repository schemas expose 5 independent self-evolution signal types/field scopes externally | Required unless self-evolution deferred |

# Epic 4: Data Ownership (Export + Account Deletion)

## Problem Statement

GDPR requires portability (Art.20) and erasure (Art.17). Users also need confidence that their research data belongs to them and can be taken away/deleted.

## Solution

**DO2**: One-click export of all local research data as an open JSON Schema zip passing ajv: industry-readable standards rather than private dumps. **DO3**: One-click account deletion clears server identity + behavior telemetry while retaining the device-level library.

## User Stories

1. As a user, I want all local research data exported to zip in one click for backup/portability.
2. As a user, I want open JSON Schema and ajv validation so other tools can read standard formats.
3. As a user, I want all objects (papers/notes/evidence-sets/evidence-refs/citation-relations/reviews) included for completeness.
4. As a user, I want export in Account for centralized management.
5. As a user, I want one-click deletion to exercise GDPR erasure.
6. As a user, I want server identity/behavior removed afterward, erasing my server footprint.
7. As a user, I want local research retained afterward, preserving assets.
8. As a user, I want explicit second confirmation/impact explanation before deletion to avoid accidents.

<a id="关键产品决策-3"></a>

## Key Product Decisions

- **Full DO2**: Produce O1 open JSON Schema from object TS interfaces in 0.3; zip export + ajv validation. Moves 0.2 §2 O1 standard outputs into 0.3.
- **DO3**: Remove server identity + telemetry, retain local device-level library independently of account deletion.
- **DO1 location cards / DO4 local-first narrative cut**, deferred to 0.4.
- Export/deletion on Settings Account tab.

## Acceptance Criteria

| # | Acceptance | Priority |

| DO-2 | Click Export My Data → zip → ajv passes | Required |
| DO-3 | Delete account → server user/behavior cleared → local library remains visible | Required |
| DO-O1 | Object JSON Schemas in repository `schema/`, covering all export object types | Required |

# Epic 6: Security and Compliance (GDPR MVP)

## Problem Statement

Public EU release requires minimum GDPR compliance and basic transport/authentication/operations security to avoid legal risk and lost trust.

## Solution

GDPR MVP: Privacy Policy / ToS, DPA signing, outsourced EU Representative, EU opt-in (Epic 3), export/deletion (Epic 4), cross-border SCC disclosure where applicable. Security: TLS 1.3, JWT + rotating Refresh, Rate Limiting/CORS, token safeStorage, Dependabot blocking high-severity vulnerabilities.

## User Stories

1. As a user, I want accessible Privacy Policy/ToS to understand processing.
2. As a user, I want policy to state server identity mapping/telemetry, OPENSCI IdP, and local research storage for informed consent.
3. As an EU user, I want applicable cross-border SCC disclosure for compliance visibility.
4. As a user, I want all API traffic encrypted with TLS 1.3, without plaintext.
5. As a user, I want API Rate Limiting for stability/abuse prevention.
6. As a product team, I want Dependabot blocking high-severity vulnerability PRs in CI for dependency security.
7. As a user, I want data-deletion requests (DO3) to exercise erasure rights.

<a id="关键产品决策-5"></a>

## Key Product Decisions

- **GDPR MVP scope**: DPO selection, formal DPIA, lawyer-drafted documents deferred to 0.4/V1 scaling triggers (1k+ EU users or charging).
- **Privacy Policy reflects new architecture**: Server identity mapping/telemetry only, OPENSCI identity provider, research local.
- **Legal entity may be a placeholder**, nonblocking; fill entity fields 30-90 days after release.
- No API Cert Pinning (desktop antipattern); update-channel pinning optional.

# Epic 7: Release Prerequisites (Lead-Time Checklist)

## Problem Statement

Many release blockers involve review/logistics/contracts rather than engineering. Without early starts, the 2-week coding window cannot absorb delays and release slips.

## Solution

Track each prerequisite: Apple/Windows signing, email domain, **new OPENSCI SSO contract freeze + readiness date**. Each has hard deadlines and deferral-assessment triggers.

## User Stories

1. As release owner, I want Apple Developer/macOS Notarization ready so Gatekeeper permits the installer.
2. As release owner, I want Windows EV Code Signing status clear by Week 1 end to decide dual-platform launch (otherwise → 0.4).
3. As release owner, I want frozen OPENSCI OAuth/OIDC contracts/readiness dates so parallel OPENSCI work does not block accounts.
4. As release owner, I want ORCID/Google OAuth confirmed as OPENSCI responsibility, avoiding duplicate applications/lead-time.
5. As release owner, I want SPF/DKIM/DMARC for product-notification email if needed so messages avoid spam; ASCI exempt if OPENSCI handles sign-in email.
6. As release owner, I want explicit started/completed/unreachable-needs-deferral statuses and deadlines to trigger timely assessments.

<a id="关键产品决策-6"></a>

## Key Product Decisions

- **OPENSCI SSO readiness is a new critical prerequisite**: Parallel OPENSCI/ASCI work during 0.3 creates moderate dependency risk; freeze contracts early.
- **ORCID/Google OAuth belongs to OPENSCI**, ASCI exempt (large lead-time reduction from north-star).
- **Windows EV determines dual-platform launch**: Decide at Week 1 end; absent EV moves all Windows work to 0.4 with macOS-only launch.
- Email domain unnecessary if OPENSCI handles all sign-in email; product-notification need remains conditional.
