## 0. 概述与定位

**0.4 把"新场景"押在 AI 最薄弱、却最高价值的认知工作上——帮研究者看见研究空白。**

战略定位：
- **产品定位**：深耕**学术个人研究者产品**（本地优先 / BYOK / Agent 主导 / 桌面）。
- **护城河**：**工作流锁定 + 个性化飞轮**。新功能按"能多深咬住工作流"来选。
- **新功能原则**：锚定 **HITL（人在环）+ 增强而非替代**——**AI 铺开前沿、用户拍板**；AI 不替用户判定"是不是创新"。

**0.4 三块**：

1. **【新功能】研究空白** —— 在用户圈定的一组文献里，AI 抽出"谁做过什么"的**对照表**，指出**没人填的空白 + 互相打架的结论**，每条可溯源，用户拍板，结果沉淀进证据集。
2. **【已有优化】证据集/笔记基础体验** —— 厘清"笔记 = 证据集里的备注"，支持随时往已有证据集补笔记/补证据；承接新功能产出的落地。
3. **【已有优化】安全边界** —— prompt/数据披露分级与脱敏。**P0 是公开发布上线门禁**，非可选项。

# Epic 1：研究空白（新功能 · 头牌）

## Problem Statement

研究者在做某主题的文献精读时，手里常有几十篇论文，但要回答"这些工作各自试了什么、哪些组合还没人做、哪些结论互相矛盾"只能靠人脑一篇篇比对，极耗时且易漏。调研证实：**从论文里抽结构化信息、做跨文献比较是当前 AI 工具最不成熟、却最高价值的环节**（自动数据抽取可用工具仅 6 个、84% 只抽标题摘要，最强复现工具准确率仅 39%；系统综述平均 67.3 周/篇）。同时，"AI 自主生成创新点"既不可靠又踩研究者最大抵触区——所以正确形态是**增强**：AI 把前沿铺成可比的对照表，用户来判断哪里是值得做的空白。

## Solution

新增**研究空白**能力（按现有能力包架构落地）：

1. 用户**圈定一组文献**（从一个证据集、或在文献库/检索结果里勾选）。
2. AI **自动提议对照表的列**（该组论文共有的可比属性），用户可增删改。
3. AI 把每篇论文填进**对照表**，**每个格子可点回原文**。
4. 系统在对照表上呈现**研究空白**：没人填的属性组合 = 空白；AI 标出结论打架处。范围**严格限定在这组论文内**。
5. 用户审阅、编辑、**拍板**哪个空白值得做；结果（对照表 + 选中的空白）**沉淀进证据集**（与 Epic 2 打通）。

**核心定位**：AI 只铺对照表、指空白；"是不是真创新"永远由用户判断，AI 不替用户下结论。

## User Stories

1. 作为研究者，我想框定我正在精读的一组论文（来自某证据集或勾选），让 AI 把它们拉成一张可比的对照表，以便一眼看清这组工作的全貌。
2. 作为研究者，我想 AI 先**提议**对照表该比哪些维度（列），但我能改（加我关心的、删没用的），以便表贴合我的研究问题。
3. 作为研究者，我想表里每个格子都能点回原文出处，以便核实、不被 AI 瞎填糊弄。
4. 作为研究者，我想系统指出"哪些维度组合还没人做过"和"哪些论文结论互相矛盾"，以便快速定位潜在的研究空白与争议点。
5. 作为研究者，我想系统说的"空白"明确是"在这组论文里"，不冒充"全世界没人做过"，以便我清楚它的边界、不被误导。
6. 作为研究者，我想自己判断哪个空白值得做（而不是 AI 替我拍"这是创新点"），以便保留我的学术判断。
7. 作为研究者，我想把这张表和我选中的空白存进证据集，以便后续围绕这个主题继续沉淀。
8. 作为研究者，我想这张表用一个清晰的表格视图呈现（可排序/筛选/点开看出处），以便审阅大表时不乱。

## Implementation Decisions（产品决定）

- **D1 输入来源**：所选文献来自**一个证据集**或在**文献库/检索结果里勾选的一组论文**——复用现有选择交互，不另造入口。
- **D2 对照表列的来源**（核心）：**AI 看完这组论文自动提议列**，用户可**增 / 删 / 改**。不做学科固定模板（太死）、不强制用户手建（太重）。
- **D3 空白判定**：① 对照表中稀疏/空的属性组合 = 空白；② AI 标注的结论冲突。**两者每条都带溯源**，且**严格限定"在所选文献内"**——产品文案与 AI 输出都不得出现"全领域/全世界没人做过"的措辞。
- **D4 沉淀**：对照表 + 用户选中的空白**写入证据集**（成为结构化笔记/证据，与 Epic 2 模型对齐）。
- **D5 用户拍板**：AI 输出止于"铺对照表 + 指空白 + 指冲突"；"哪个空白值得做 / 是否创新"由用户判定，AI 不输出该结论。
- **能力包形态**：作为新能力包接入现有注册中心（场景 Agent 负责澄清+抽取编排、Skill 负责对照表/空白产出规范、复用现有文献解析/LLMWiki 作抽取语料层）。
- **右侧视图（最小化，不过度工程）**：本功能需要一个新的**表格视图**展示对照表。**0.4 只新增这一个视图即可，不为它先建"可插拔 renderer 通用框架"**——只有一个新视图时，通用框架属过度设计；待未来出现第 2、3 个新视图再抽象。

## 🚧 关键风险与前置验证（动工核心前必做）

**抽取质量是本功能的命门，也是当前业界最不成熟的能力**（最强工具准确率仅 39%）。**核心实现前先做一个小验证 spike**：
- 拿**真实的 15–20 篇论文**（用户实际领域），跑 AI 自动提议列 + 填格。
- 量化三件事：① 抽取**准确率**（格子填对的比例，人工抽样核）；② 一次能稳定处理的**论文篇数上限**；③ 用户 BYOK key 跑一次的**真实成本/时延**。
- 据此再定抽取做到多深、对照表规模上限、是否分批。
- **原则**：守"证据优先于承诺"——不拿未验证的抽取能力当交付承诺。

## Testing / 验收（验外部行为）

- 给定一组论文 → 系统产出对照表，列为 AI 提议且用户可增删改；每个非空单元格可溯源到原文锚点。
- 空白与冲突标注**只在所选文献范围内**成立；产品文案/AI 输出**零**"全领域没人做过"措辞（专门回归测试）。
- 对照表 + 选中空白可写入证据集并读回完整、保序。
- AI 输出中**不出现**"这是创新点/此方向 novel"类替用户拍板的结论（回归测试）。
- 抽取 spike 的准确率/篇数/成本三项有量化结论后，才进入核心实现。

## Out of Scope

- **全前沿版**（空白范围从"所选文献"扩到"整个领域所有论文"）→ 0.5，依赖文献深钻全套语料就位。
- 自动生成具体研究主张的能力 → 不做（仅在对照表基础上做提示，且仍由用户拍板）。
- 可插拔 renderer 通用框架 → 不做（最小化只加一个表格视图）。

# Epic 2：证据集/笔记基础体验（已有优化）

## Problem Statement

当前"证据集 / 笔记"存在场景混淆：笔记只能在文献/综述里划词创建、必依附一个证据集且只能有一条；补充证据只能在 Agent 对话场景里选已有集，详情页没有直接入口。用户心智里，**笔记就是证据集里的备注信息**，且希望**随时**往一个已有证据集补笔记或补证据条目。

## Solution

夯实证据集/笔记的基础体验，对齐"证据集 = 用户围绕一个主题沉淀材料的容器；笔记 = 容器里的备注"心智：
- 证据集详情页提供**直接补证据 / 补笔记**入口（不再只限 Agent 对话场景）。
- 一个证据集可有**多条笔记**（不再只能编辑唯一一条）。
- 笔记定位为"证据集里的用户备注"，与证据并列为容器成员。
- 与 Epic 1 打通：研究空白的产出（对照表 + 选中空白）作为结构化材料沉淀进证据集。

## User Stories

1. 作为用户，我想在证据集详情页直接补充证据（不必回到 Agent 对话），以便随手扩充材料。
2. 作为用户，我想在一个证据集里新增多条笔记（备注），以便记录对不同材料的不同解读。
3. 作为用户，我想笔记就是挂在证据集上的备注，与证据并列、可分别管理，以便心智清晰不混淆。
4. 作为用户，我想删除证据集里某条笔记或某个证据而不影响其余，以便精细管理。
5. 作为用户，我想证据仍可点击溯源到文献段落/综述句子/对话消息，以便保持可追溯。
6. 作为用户，我想研究空白的结果能存进证据集，以便围绕主题继续沉淀。

## Implementation Decisions

- 范围 = **基础体验**：补证据/补笔记入口 + 一集多笔记 + 笔记/证据并列管理。一条笔记/证据同属多个证据集的多归属能力本期不要求，可按需后续放开；本期以"随时补、可多条"为底线。
- 复用既有 `notes:*` / `evidenceSets:*` 通道与现有证据集服务；若涉及 IPC 变更走四联同步。
- 与 Epic 1 的衔接点：定义"对照表/空白"如何作为证据集成员落库（结构化笔记或带结构的证据条目，具体形态实现时定，验收只验"可存可读回"）。

## Testing / 验收

- 详情页可直接补证据、补多条笔记；删单个成员不影响其余。
- 笔记与证据在容器内并列、各自可管理、证据可溯源。
- Epic 1 产物可写入证据集并完整读回。

## Out of Scope

多归属交互、双向链接/知识图谱、证据集协作/分享、证据集导出独立格式。

# Epic 3：安全边界（已有优化 · 上线门禁）

## Problem Statement

ASCI 即将面向用户开放。当前内部 prompt（master/子 Agent/judge prompt）、原始工具输入输出、思考过程、敏感数据（密钥/路径/用户研究内容）会经 debug copy、权限弹窗 IPC、能力包配置页、导出、日志、第三方 telemetry 等出口**泄露给用户面或外部平台**。公开发布前必须收口。

## Solution

落地方案见 `docs/specs/0.4.0/prompt-disclosure-redaction-spec.md`（自包含、可独立落地），核心：
- L0–L4 数据披露分级 + 默认行为矩阵。
- 分层脱敏（shared 同步原语 / main 编排格式化+审计 / renderer 自洗），复用现有 telemetry 脱敏基建（`redact.ts` / `event-registry` / Sentry scrubber），不另造旁路。
- prompt registry / fingerprint（出口只引用 id/version/hash）。

## 0.4 范围与优先级

- **P0（= 公开发布上线门禁，0.4 必做）**：spec §10 的 P0-0~P0-8（最小脱敏基建 + debug copy / 权限 / AskUser / ExitPlan / 能力包 UI / 第三方 telemetry / error monitoring / 导出 收口）。
- **P1（上线前应改，0.4 视窗口纳入）**：spec §10 的 P1-1~P1-9（完整 prompt registry、发布产物扫描、SDK/plugin 注入面实测等）。
- **P2（上线后治理）**：→ 0.5+。

## Testing / 验收

采用 spec §15 的上线门禁清单（debug copy / 导出 / 权限 IPC / 能力包配置页 / 第三方 telemetry / session replay / error monitoring / 打包产物扫描 / SDK 注入面 的逐项"0 命中"验收）。

# 前置探索（面向 0.5，不计入 0.4 交付）：Google Scholar 抓取可行性

> **追踪 issue**：[#722 [spike] GS 抓取可行性探索](https://github.com/OPENSCI-Labs/ASCI-Alpha/issues/722)

## 为什么放进 0.4

GS 是**无 API 源接入**的标杆源（[ADR-014](../../adr/ADR-014-non-api-sources-and-demand-driven-fill.md) D2/D3），覆盖 OpenAlex 缺的长尾（灰文献、引文发现、非英文、学位论文、部分非 OA）。它的**正式接入是 0.5 新功能**（0.5 PRD Epic 5）；但"我们的 user-local 抓取到底能不能稳定抓到 GS 论文"是技术未知数——GS 在[失败触发扩源 spec](../lit-search-failure-source-expansion-spec.md) §4.2 曾因抓取脆 / 封 IP 被列黑名单死源。**必须先在 0.4 期间并行探索出结论**，0.5 才能据此承诺做成什么样（守"证据优先于承诺"）。

**边界**：0.4 **只探索、不做正式集成**；作为可并行、不阻塞研究空白主线的独立 spike。

## 第一优先级 + fallback（三层降级链）

第一优先级 = 让检索 Agent 经"我们自己的实现方式"（user-local 抓取）**直接抓 GS**；同时定出 fallback：

```
检索 Agent 要 GS 结果
 ├─ L1 主路径：user-local 抓取（跑用户本地 IP/会话 · 成本=0 · 法律风险分散到用户）
 ├─ L2 fallback：第三方 SERP API（SerpApi 等，用户自配 key = BYOK，ASCI 不代付）
 └─ L3 安全地板：一键直达 GS 网页（永远可用 · 零风险 · 抓取全挂时保底）
```

> ASCI 服务端**永不自抓**（ADR-014 D2：IP 秒封 + 独担法律成本 + 破 BYOK 模型）。

## 探索要产出什么（解锁 0.5 的门）

| # | 探索产出 | 量化口径 |
|---|---------|---------|
| GS-E1 | L1 在真实反爬下的可用率 | 可用率 / 延迟 / CAPTCHA 命中率 / 封锁率（ADR-014 D3）|
| GS-E2 | 选定并验证一条 user-local 抓取技术路径 | headless 选型 + 反爬应对 + GS 页面解析，出最小 PoC（"查询 → 结构化结果 + 回链"跑通）|
| GS-E3 | fallback 链可行性 | L2 SERP API 接入成本 / BYOK 形态 + L3 直达 GS 边界 |
| GS-E4 | 法律边界 | 法务确认"提供抓取工具 vs 代为抓取"的 ToS / 声誉边界 |

**过阈判定**：探索达标 → 0.5 把 L1 做成主路径；不达标 → 0.5 以 L2 为主、L1 尽力而为、L3 永远在。

| 实验设计 | → 0.6+（需先谈实验室合作）|

## 6. 依赖与实施顺序

```
并行起步：
  Epic 3 安全边界 P0（上线门禁，独立、可立即开工，复用现有脱敏基建）
  Epic 2 证据集/笔记基础体验（增量、低风险）
  Epic 1 前置 spike：抽取质量/篇数/成本验证（拿真实论文跑）
  [面向 0.5] GS 抓取可行性探索 spike（user-local 抓取 + fallback 链；独立并行，结论交 0.5 Epic 5）

spike 出结论后：
  Epic 1 核心：所选文献 → 对照表 → 研究空白 → 拍板 → 沉淀（与 Epic 2 衔接）
```

依赖：Epic 1 沉淀环节 ⬅ Epic 2 的证据集补充能力；Epic 1 核心 ⬅ 抽取 spike 结论。Epic 3 独立。GS 探索独立并行、不阻塞任何 0.4 交付。
