## 0. Overview and Positioning

**0.4 bets its new scenario on cognitive work where AI is weakest yet value is highest: helping researchers see research gaps.**

Strategic positioning:
- **Product**: Focus on an **individual academic researcher product** (local-first / BYOK / Agent-led / desktop).
- **Moat**: **Workflow retention + personalization flywheel**. Choose features by how deeply they embed in workflows.
- **Feature principle**: Anchor on **HITL (human in the loop) + augmentation rather than replacement**: **AI lays out the frontier; users decide**. AI never decides whether something is innovative for the user.

**Three parts in 0.4**:

1. **[New] Research gaps**: Within user-selected literature, AI extracts a **comparison table** of who did what, highlights **unfilled gaps + conflicting conclusions**, with provenance for each. Users decide, and results accumulate in evidence sets.
2. **[Improvement] Evidence set/notes foundations**: Clarify "notes = annotations in evidence sets," allowing notes/evidence to be added to existing sets anytime and giving new-feature outputs a home.
3. **[Improvement] Security boundaries**: Prompt/data disclosure classification and redaction. **P0 is a public-release gate**, not optional.

# Epic 1: Research Gaps (New · Flagship)

## Problem Statement

Researchers closely reading dozens of papers on a topic must manually compare them to answer "what did each try, which combinations remain untried, and which conclusions conflict?" This consumes time and misses details. Research confirms **structured extraction and cross-paper comparison are among AI tools' least mature yet highest-value steps** (only 6 usable automatic extraction tools; 84% extract only titles/abstracts; strongest reproduced tool accuracy only 39%; systematic reviews average 67.3 weeks each). Meanwhile, autonomous AI-generated innovation is unreliable and triggers researchers' strongest resistance. The appropriate form is **augmentation**: AI organizes the frontier into comparable tables; users judge promising gaps.

## Solution

Add **research-gap** capability through existing capability-package architecture:

1. User **selects a group of papers** (from an evidence set or selected in library/search results).
2. AI **proposes comparison-table columns** (comparable attributes shared by these papers); user adds/deletes/edits.
3. AI fills each paper into the **comparison table**; **each cell links to original text**.
4. Present **research gaps** on the table: Empty attribute combinations = gaps; AI highlights conflicting conclusions. Scope **strictly limited to these papers**.
5. User reviews, edits, and **decides** which gaps merit work; results (table + selected gaps) **persist in an evidence set** (connected to Epic 2).

**Core positioning**: AI organizes comparisons and points to gaps; users always judge actual innovation, and AI does not conclude for them.

## User Stories

1. As a researcher, I want to select papers I am closely reading (from an evidence set or selection) and have AI organize a comparison table, so I can see this work at a glance.
2. As a researcher, I want AI to **propose** comparison dimensions (columns), while I can add relevant ones and remove useless ones, so the table fits my question.
3. As a researcher, I want every cell to link to its original source, so I can verify it and avoid fabricated AI entries.
4. As a researcher, I want the system to identify untried dimension combinations and contradictory conclusions, so I can locate potential gaps and disputes quickly.
5. As a researcher, I want "gaps" explicitly limited to these papers rather than claims that nobody worldwide has done something, so I understand the boundary and am not misled.
6. As a researcher, I want to judge which gaps merit work myself, rather than AI declaring innovation, so I retain academic judgment.
7. As a researcher, I want to save the table and selected gaps into evidence sets, so I can continue accumulating materials around the topic.
8. As a researcher, I want a clear table view with sorting/filtering/source inspection, so large-table review stays manageable.

<a id="implementation-decisions产品决定"></a>

## Implementation Decisions (Product Decisions)

- **D1 Input sources**: Papers from **one evidence set** or **a selection in library/search results**; reuse existing selection interactions without another entry point.
- **D2 Column sources** (core): **AI proposes columns after reading the group**, and users may **add / delete / edit**. No rigid discipline templates or burdensome mandatory manual creation.
- **D3 Gap detection**: ① Sparse/empty attribute combinations; ② AI-annotated conflicting conclusions. **Every item in both has provenance**, **strictly within selected literature**. Neither product copy nor AI output may claim "nobody in the field/world has done it."
- **D4 Persistence**: **Write table + user-selected gaps into evidence sets** as structured notes/evidence, aligned with Epic 2.
- **D5 User decides**: AI stops at table organization + gaps + conflicts; users decide worth and innovation, and AI never outputs that conclusion.
- **Capability-package form**: New package in existing registry (scenario Agent handles clarification/extraction orchestration; Skill defines table/gap outputs; existing literature parsing/LLMWiki supplies extraction corpus).
- **Right-side view (minimal, no overengineering)**: A new **table view** is required. **0.4 adds only this view, without first building a generic pluggable renderer framework**. With one view such a framework is premature; abstract when a second/third appears.

<a id="-关键风险与前置验证动工核心前必做"></a>

## 🚧 Key Risk and Prerequisite Validation (Required Before Core Work)

**Extraction quality determines this feature's survival and is among the industry's least mature capabilities** (strongest tool only 39% accurate). **Run a small validation spike before core implementation**:
- Use **15–20 real papers** in the user's actual discipline; test AI column proposals + cell filling.
- Quantify: ① Extraction **accuracy** (proportion of correct cells, manually sampled); ② Stable **maximum papers per run**; ③ **Actual cost/latency** with user BYOK.
- Use findings to set extraction depth, table-size limits, and batching.
- **Principle**: Evidence precedes promises; do not promise unverified extraction capability.

<a id="testing-&#45;验收验外部行为"></a>

## Testing / Acceptance (External Behavior)

- Given papers → system produces a table with AI-proposed, user-editable columns; every nonempty cell traces to an original-text anchor.
- Gap/conflict annotations apply **only within selected literature**; **zero** field-wide novelty claims in copy/AI output (dedicated regression).
- Table + selected gaps write into evidence sets and read back completely, preserving order.
- AI output **never** substitutes for user judgment with "this is innovative/this direction is novel" conclusions (regression).
- Core implementation begins only after quantified extraction accuracy/paper-count/cost spike conclusions.

## Out of Scope

- **Full-frontier edition** (expand gaps from selected papers to the entire field) → 0.5, dependent on full deep-literature corpus readiness.
- Automatically generating specific research propositions → not planned (only table-based suggestions, still user-decided).
- Generic pluggable renderer framework → not planned (add one minimal table view).

# Epic 2: Evidence Set/Notes Foundations (Improvement)

## Problem Statement

Current evidence sets/notes confuse scenarios: Notes can only be created by selecting text in literature/reviews, must belong to an evidence set, and only one is allowed. Adding evidence requires selecting an existing set in Agent conversation, with no direct details-page entry. Users understand **notes as annotations in evidence sets** and want to add notes/evidence to existing sets **anytime**.

## Solution

Strengthen foundations around "evidence set = topic-material container; note = annotation in that container":
- Details pages provide **direct add-evidence / add-note** actions, beyond Agent conversation.
- One set supports **multiple notes**, rather than editing one unique note.
- Notes are user annotations in evidence sets, alongside evidence as container members.
- Epic 1 connects: Research-gap outputs (table + selected gaps) accumulate as structured materials.

## User Stories

1. As a user, I want to add evidence from set details without returning to Agent conversation, so I can expand materials easily.
2. As a user, I want multiple notes/annotations in a set, so I can record different interpretations of materials.
3. As a user, I want notes attached to sets alongside evidence and independently manageable, so the model is clear.
4. As a user, I want deleting one note/evidence item to leave others unaffected, for granular management.
5. As a user, I want evidence still linked to paper passages/review sentences/conversation messages, preserving traceability.
6. As a user, I want research-gap results saved into evidence sets to continue building topic materials.

## Implementation Decisions

- Scope = **foundational experience**: Add-evidence/add-note entry + multiple notes + parallel management of notes/evidence. Multiple-set membership for one note/evidence item is not required now; may follow later. Minimum: "add anytime, multiple entries."
- Reuse `notes:*` / `evidenceSets:*` channels and evidence-set services; synchronize four IPC layers if changed.
- Epic 1 connection: Define table/gap persistence as set members (structured notes or evidence entries; choose during implementation; acceptance checks only save/read-back).

<a id="testing-&#45;验收"></a>

## Testing / Acceptance

- Add evidence/multiple notes directly in details; deleting one member leaves others intact.
- Notes/evidence coexist and are independently manageable; evidence retains provenance.
- Epic 1 outputs persist into sets and read back completely.

## Out of Scope

Multiple-membership interactions, bidirectional links/knowledge graphs, evidence-set collaboration/sharing, standalone evidence-set export formats.

# Epic 3: Security Boundaries (Improvement · Release Gate)

## Problem Statement

ASCI is approaching public availability. Internal prompts (master/sub-Agent/judge), raw tool inputs/outputs, thinking, and sensitive data (keys/paths/user research) currently **leak to user surfaces or external platforms** through debug copy, permission-popup IPC, capability configuration, exports, logs, and third-party telemetry. Restrict before public release.

## Solution

See self-contained, independently implementable `docs/specs/0.4.0/prompt-disclosure-redaction-spec.md`:
- L0–L4 disclosure classification + default behavior matrix.
- Layered redaction (shared synchronous primitives / main orchestration-formatting+audit / renderer self-scrubbing), reusing existing telemetry redaction (`redact.ts` / `event-registry` / Sentry scrubber), without parallel paths.
- Prompt registry / fingerprints (outputs reference only id/version/hash).

- **P2 (post-launch governance)**: → 0.5+.

# Prerequisite Exploration (For 0.5, Outside 0.4 Deliverables): Google Scholar Scraping Feasibility

> **Tracking issue**: [#722 [spike] GS scraping feasibility exploration](https://github.com/OPENSCI-Labs/ASCI-Alpha/issues/722)

<a id="为什么放进-04"></a>

## Why Include It in 0.4

GS is the benchmark for **non-API sources** ([ADR-014](../../adr/ADR-014-non-api-sources-and-demand-driven-fill.md) D2/D3), covering OpenAlex's missing long tail (gray literature, citation discovery, non-English, dissertations, some non-OA). **Formal integration is a 0.5 feature** (0.5 PRD Epic 5), but stable user-local GS retrieval is technically unknown: [failure-triggered source expansion spec](../lit-search-failure-source-expansion-spec.md) §4.2 blacklisted it as dead due to fragile scraping/IP blocking. **Reach a conclusion through parallel exploration during 0.4**, so 0.5 commitments rest on evidence before promises.

**Boundary**: 0.4 **explores only, with no formal integration**; separate parallel spike, nonblocking to research-gap work.

<a id="第一优先级-&#45;fallback三层降级链"></a>

## First Priority + Fallback (Three-layer Degradation Chain)

First priority: Search Agent **scrapes GS directly** through our own user-local implementation; also define fallback:

```
Search Agent requests GS results
 ├─ L1 primary: user-local scraping (user IP/session · cost=0 · legal risk distributed to users)
 ├─ L2 fallback: third-party SERP API (SerpApi, etc.; user key = BYOK, ASCI does not pay)
 └─ L3 safety floor: direct GS webpage link (always available · zero risk · fallback if all scraping fails)
```

English guide: Agent requests GS results → L1 primary user-local scraping (user IP/session, zero cost, legal risk distributed to users) → L2 third-party SERP API such as SerpApi (user BYOK, no ASCI payment) → L3 direct GS webpage link (always available, zero risk, fallback when scraping fails).

> ASCI servers **never scrape directly** (ADR-014 D2: immediate IP blocks, sole legal burden, broken BYOK model).

<a id="探索要产出什么解锁-05-的门"></a>

## Required Exploration Outputs (Unlocking 0.5)

| # | Output | Quantification |
|---|---------|---------|
| GS-E1 | L1 availability under actual anti-scraping | Availability / latency / CAPTCHA rate / blocking rate (ADR-014 D3) |
| GS-E2 | Select and validate one user-local approach | Headless selection + anti-scraping response + GS parsing; minimal PoC from query → structured results + backlinks |
| GS-E3 | Fallback feasibility | L2 SERP API cost / BYOK form + L3 direct-link boundaries |
| GS-E4 | Legal boundaries | Legal confirmation of ToS / reputation boundaries between providing scraping tools and scraping on users' behalf |

**Threshold decision**: If exploration passes → L1 primary in 0.5; otherwise → L2 primary, L1 best effort, L3 always retained.

## 6. Dependencies and Implementation Order

```
Parallel starts:
  Epic 3 security P0 (release gate, independent, immediate start, reuse redaction infrastructure)
  Epic 2 evidence set/notes foundations (incremental, low risk)
  Epic 1 prerequisite spike: extraction quality/paper count/cost (real papers)
  [For 0.5] GS scraping feasibility spike (user-local + fallback chain; independent, parallel, feeds 0.5 Epic 5)

After spike conclusions:
  Epic 1 core: selected papers → comparison table → research gaps → user decision → persistence (connects Epic 2)
```

English guide: Parallel starts comprise Epic 3 security P0 (independent immediate release gate, reusing redaction), Epic 2 evidence-set/notes foundations (incremental, low risk), Epic 1 real-paper extraction quality/count/cost spike, and independent 0.5 GS feasibility/fallback spike feeding Epic 5. After spike findings, implement Epic 1 selected literature → table → gaps → decision → persistence, connected to Epic 2.

Dependencies: Epic 1 persistence ⬅ Epic 2 addition capabilities; Epic 1 core ⬅ extraction-spike findings. Epic 3 independent. GS exploration is independent/parallel and blocks no 0.4 deliverable.

<a id="7-风险"></a>

## 7. Risks

| Risk | Impact | Mitigation |
|------|------|------|
| Extraction quality below target (industry SOTA only 39%) | Feature fails to deliver value | **Validate spike first**; set depth from findings, reduce scope if needed |
| Gaps misread as worldwide novelty | Trust collapses | Strict selected-literature limits in copy/AI output, dedicated regression |
| Security P0 delayed | **Public release blocked** | Highest-priority independent P0; existing spec acceptance checklist gates release |
| Large scope (new feature + 2 improvements) | Delay | Three parallel parts; Epic 1 spike controls uncertainty, reduce table scale if needed |
| GS exploration consumes mainline capacity | Research gaps delayed | Exploration only, no integration, parallel independent owner; failed exploration affects no 0.4 deliverable |
