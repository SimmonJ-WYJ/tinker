## 0. 概述与定位

**0.5 一句话：把 ASCI 的"文献前门"从实时打 flaky 外部 API，升级为自建的、又快又准的检索数据服务；同时让研究空白从"用户手头几十篇"扩到"整个领域所有论文"。**

两块互为因果：
- **【已有优化/基础设施】文献深钻全套** —— 自建 OpenAlex 论文元数据库 + AI 智能检索/重排 + 重点领域 OA 全文预解析加速。这是 ASCI 第一个**数据服务底座**。
- **【新功能】研究空白·全前沿版** —— 有了全量语料，"找空白"的圈定范围从用户手头的几十篇，扩到整个领域；这是文献深钻造好后自动解锁的新价值。

设计哲学：**不囤论文，囤相关性**。检索/重排默认跑用户 BYOK（ASCI 服务端零每查询推理成本），服务端只托管 index/语料，守本地优先 + 隐私红线。

# Epic 1：文献语料底座（已有优化/基础设施）

## Problem Statement

现状文献检索 = 本地 MCP 对 15+ 外部开放 API **实时扇出**、无自建索引/无缓存。实测主力源会整源失败、同类查询返回数 0↔45 剧烈跳变、备用源慢且差。三痛点：检索**不全** / 检索**不准** / 精读**慢**。

## Solution（采用 ADR-013「部分自建分层」）

- **自建 OpenAlex 全量元数据 index**（落 ASCI 服务端，0.3.0 已开的云服务器/云数据库扩出检索 workload）——覆盖长尾，检索打本地 index 不再实时扇出。
- **缓存可合法再分发的 OA 全文**（peS2o/S2ORC 的 ODC-By、PMC oa_comm 的 CC0/CC-BY），守许可红线；arXiv/非 OA/NC-ND **不入库**，按需现抓 + 外链。
- 无 API 源（Google Scholar 等）按 ADR-014：**用户本地实时现抓 + 外链、永不落库**，ASCI 服务端永不自抓。

## User Stories

1. 作为研究者，我想同一查询**毫秒级**返回、不再因外部源挂掉而搜不到，以便检索可靠。
2. 作为研究者，我想检索覆盖到长尾文献（不只热门库），以便不漏关键工作。
3. 作为研究者，我想 Google Scholar 这类没 API 的源也能补进来（现抓+外链），以便覆盖灰文献/引文/非英文。

## Implementation Decisions

- 架构、许可红线、GDPR、成本/新鲜度管道**全部采用 ADR-013/014**，本 PRD 不复述。
- **同步修订 ADR-002**：服务端新增检索 workload（index 引擎选型 ES/OpenSearch/Typesense、存储、新鲜度管道）。

## 🚧 前置 spike（ADR-013 已挂，动工前必做）

1. **三档真实月成本 / 工程人月**（内部 infra spike，公开查不到）。
2. **agentic 检索/重排评测集**（自建小评测集量化"扛专业质疑"，目前仅重排层单点证据 CoRank）。

> **GS 接入可行性原为本块 spike③，现前移到 0.4 期间并行探索**（见 [0.4 PRD「前置探索」块](../0.4.0/0.4.0-prd.md)）；0.5 据其结论在 **Epic 5** 正式落地，不再占用 Epic 1 的动工闸。

## 验收

- 同一查询命中本地 index、毫秒级返回、不依赖外部源存活。
- 语料抽样核验每篇带 license 元数据、NC/ND 已剔除；arXiv 结果带回链不缓存。
- 法务确认逐篇上游 license 过滤策略。

# Epic 2：智能检索与重排（已有优化 · 差异化核心）

## Problem Statement

裸词面/扇出召回相关性差。研究者要"随便一搜，秒回一二十篇紧扣专业"。

## Solution（ADR-013 P2）

在语料之上做软件差异化层：**agentic 迭代检索**（沿引文链/查询演化多轮）+ **混合召回**（BM25 ⊕ dense）+ **LLM 重排**（把 canonical/紧扣专业的顶到前 N）。**默认跑用户 BYOK key**，ASCI 服务端零每查询推理成本。接现有 lit-search 能力包（searcher/relevance-scorer 子 Agent），不另起炉灶。

## User Stories

1. 作为研究者，我想随便一搜就秒回一二十篇紧扣我专业方向的文献，以便不用反复调关键词。
2. 作为研究者，我想复杂查询下系统能多轮迭代（沿引文、演化查询）而非一次性召回，以便复杂题也能搜全。
3. 作为研究者，我想智能检索跑我自己的 key、不额外花 ASCI 的钱，以便服务可持续、我也可控。

## 产品决策（2026-06-24 澄清）

- **agentic 迭代可见但折叠**：多轮迭代（沿引文链 / 查询演化）对用户透明——收进可展开的"检索工作步骤组"（复用 `search-plan-confirm` 起手计划 + `execution-step-grouping` 过程组），默认折叠、想审就展开。可信靠"可审"，流畅靠"默认折叠"。
- **BYOK 成本：轻提示 + 事后可见 + 内部兜底，不硬控**：搭车 `search-plan-confirm` 在确认计划处说明"多轮迭代 · 跑你的 key"；搜后显示本次实际用量；防失控靠 agentic 循环的内部回合上限（非用户侧预算闸）。用户侧硬预算闸 → 0.6 按实战反馈再议。
- **降级阶梯（拒绝贵的不空手）**：检索方案确认提供四档——`确认执行（智能检索 · 多轮）` / `我来调整` / `单轮检索（混合召回 + 一次重排 · 更省）` / `取消`。拒绝多轮 → 落到「单轮检索」而非零结果，与 ASCI 的 L1/L2/L3 fallback 设计语言一致。「单轮检索」命名对齐 CONTEXT.md「智能检索」术语（多轮 vs 单轮，不用"快速"以免与"秒回"卖点打架）。

## 验收

- 评测集上混合检索 recall 较裸 BM25 显著提升；LLM 重排把 canonical 顶到前 N（golden path 走查"随便一搜秒回紧扣专业"）。
- 审计调用链：推理在用户 channel，服务端只查 index。
- 现有 lit-search 包指向新 index + 重排即生效。

## Out of Scope

全量语义向量 embedding（2 亿+，ADR-013 不做）；0.6 查询飞轮（撞隐私红线，0.6 opt-in 再碰）。

# Epic 3：重点领域全文加速（已有优化）

## Problem Statement

逐篇精读 = 现抓 PDF → 解析 → RAG，分钟级，拖慢综述。

## Solution（ADR-013 P3 + ADR-014 需求驱动填充）

- 复用开源 SOTA 解析（MinerU/olmOCR），不自研。
- 命中可合法缓存的 OA 全文语料的论文，精读**秒开**（预解析+预切分）。
- 未命中的按需现抓+解析+RAG，结果可缓存（守许可）；OA 论文走 ADR-014 需求驱动语料填充（去关联信号 + 服务端自取自解析，仅 OA 入共享缓存）。

## User Stories

1. 作为研究者，我想打开重点领域论文的精读时秒开（而非等分钟级解析），以便综述提速。
2. 作为研究者，我想检索到的论文能直接深读问答（检索→精读闭环），以便不用切工具。

## 产品决策（2026-06-24 澄清）

- **全文三态 · 事前标 + 事中有信息进度**（沟通快慢落差，避免"像坏了"）：
  - ① 已就绪（命中可合法缓存 OA 全文）→ 秒开；
  - ② 需现抓（OA 未缓存 / arXiv）→ 可读但要等，事中显式"获取 PDF → 解析 → 建索引"进度（非裸转圈）；
  - ③ 仅外链（非 OA / CC-NC/ND）→ 受许可限制只跳源站，明确标注"非故障"。
  - 论文条目上**事前标三态**（搭车检索结果元数据，零额外成本）；① 不啰嗦。
- **R4 检索→精读闭环必 ship**（scope-boxed 下从"可降级"转必做）：检索结果一键进精读问答，不切工具 / 不重导入；覆盖范围与三态一致（① 秒开 / ② 现抓后可读 / ③ 仅外链不支持精读）。

## 验收

- 命中语料的论文打开精读 < 秒级；未命中的按需现抓可用且缓存合规。
- 解析质量/速度达基线、未自研解析器。

# Epic 4：研究空白·全前沿版（新功能）

## Problem Statement

研究空白·小版限定在"用户圈定的几十篇"内——可信但范围窄。研究者真正想知道的是"**在整个领域里**，这个方向是不是真的没人做过"。这一步需要全量语料支撑、且若做不好会滑回"AI 瞎判新颖性"的陷阱，因此放在文献深钻造好之后，建立在可信的语料底子上。

## Solution

把研究空白（对照表 + 空白判定 + 用户拍板，形态不变）的**所选文献从"用户手头几十篇"扩到"智能检索召回的领域级语料"**：
- 用户给一个研究方向 → 智能检索（Epic 2）召回该方向的领域级文献 → 在其上建对照表 → 呈现领域级研究空白。
- **可信底线仍守**：每条空白/冲突可溯源；范围限定"在召回的这批领域文献内"，并**显式披露召回边界**（搜了哪些源、覆盖范围、可能漏什么），不主张"绝对全世界没人做过"。
- 用户拍板不变；AI 不下"这是创新点"的结论。

## User Stories

1. 作为研究者，我想给一个研究方向，AI 在整个领域的文献里帮我铺出"做过什么、哪里是空白"，以便评估方向的新颖性与机会。
2. 作为研究者，我想系统明确告诉我它搜了哪些范围、可能漏什么，以便我清楚这个"空白"的可信边界。
3. 作为研究者，我想沿用一致的对照表 + 拍板体验，只是范围更大，以便平滑过渡。

## Implementation Decisions

- 复用研究空白的全部产品形态（对照表 / 空白判定 / 拍板 / 沉淀证据集，0.4 [research-gap-spec](research-gap-spec.md) · [#708](https://github.com/OPENSCI-Labs/ASCI-Alpha/issues/708)），**最大化复用、只动三处：换输入源 + 扛规模 + 强披露**。
- **输入：双模式**（2026-06-24 澄清 4.2）——
  - 保留 0.4「选定文献内」模式（用户圈一组论文，范围紧、可信高），**不回退**；
  - 新增「领域级召回」模式（用户给自然语言研究方向 → 智能检索召回）；
  - 召回这一步**复用 E2 `search-plan-confirm`**：用户在确认检索方案时即亲手塑形召回边界（与召回边界卡同源——可信不是事后贴标签，是事前参与划定）；
  - 可选增强：`@` 提及种子论文锚定 / 偏置召回（复用 0.4 at-mention 栈）。
- **召回边界卡：扩展 0.4 可信底线（research-gap-spec §5.5），不另造**（2026-06-24 澄清 4.1）——把"基于你选的 N 篇"升级为**常驻、不可关**的召回边界卡，载明：① 搜了哪些源、② 覆盖边界（语言 / 时间窗 / 仅 OA-indexed）、③ 明确可能漏什么（非英文 / 灰文献 / 未索引长尾）。0.4 的措辞硬过滤 + 回归测试照跑（GF3）。这是范围扩到领域级后的**承重守门**，顶住"误读成全前沿"风险。
- **扛规模：两层结构**（2026-06-24 澄清 4.3）——领域级召回可能上百上千篇，而对照表为几十篇设计、逐格抽取有篇数上限（0.4 GM7 spike），故召回与对照表之间**必须缩减**：
  - 第 ① 层 领域概览：召回语料按主题聚类（便宜 · 无逐格抽取），承载召回边界卡、体现"全前沿"的"全"；
  - 第 ② 层 下钻主题 → 0.4 对照表原样跑（抽取 + 组合空白 + 结论冲突 + 拍板 + 沉淀），限该主题可控子集内（守 0.4 GM7 抽取 spike 的篇数上限）；
  - 降级：聚类难产 → 退"rerank 取 top-N 单表 + 明确披露仅 top-N"（兜底，**非首选**——只铺 top-N 会丢长尾、背叛全前沿承诺）。
- 依赖 Epic 1–3（语料 + 智能检索 + 全文加速）就位；复用 0.4 research-gap form 需其先落地（[#708](https://github.com/OPENSCI-Labs/ASCI-Alpha/issues/708)）。

## 验收

- 给定研究方向 → 召回领域级语料 → 产出领域级对照表与研究空白；每条可溯源。
- 召回边界（源/覆盖/局限）显式呈现给用户；AI 输出**不出现**"全世界绝对没人做过/这是创新点"措辞（回归测试）。

## Out of Scope

跨领域的自动研究主张生成；实验设计（→ 0.6+）。

# Epic 5：无 API 源接入 / GS 直抓（新功能）

## Problem Statement

0.5 的智能检索（Epic 2）跑在 OpenAlex 自建 index 上，覆盖**开放世界元数据长尾**——但仍有 OpenAlex 覆盖不到的：灰文献、引文发现、非英文、学位论文、部分非 OA。这些大量散落在**不提供 API 的平台**上，Google Scholar 是标杆。研究者"搜不全"的痛，有一块就卡在这里。GS 没有 API、数据 ToS 禁抓、全文多非 OA 不可缓存——既是高价值补充，又是技术/法律双重难点（[失败触发扩源 spec](../lit-search-failure-source-expansion-spec.md) §4.2 曾列其为黑名单死源）。

## Solution（ADR-014 D1–D3）

让检索 Agent 经"我们自己的实现方式"直接抓 GS，结果**实时现抓 + 外链、永不落 Corpus**（守许可红线，与 ADR-013 一致）。抓取**默认跑用户本地**，三层降级链：

```
检索 Agent 要 GS 结果
 ├─ L1 主路径：user-local 抓取（跑用户本地 IP/会话 · 成本=0 · 法律风险分散到用户）
 ├─ L2 fallback：第三方 SERP API（SerpApi 等，用户自配 key = BYOK，ASCI 不代付）
 └─ L3 安全地板：一键直达 GS 网页（永远可用 · 零风险 · 抓取全挂时保底）
```

- **ASCI 服务端永不自抓**（ADR-014 D2：IP 秒封 + 独担法律成本 + 破 BYOK 模型）。
- **过阈判定**（据 0.4 探索结论定档）：达标 → L1 做成主路径；不达标 → 以 L2 为主、L1 尽力而为、L3 永远在。
- 0.5 只接 **GS 一个标杆源**（观察档）；扩源（ResearchGate / CNKI / 万方 / 出版商页）→ 0.6/V1，以 GS 实战结果为门。

## User Stories

1. 作为研究者，我想检索覆盖到 GS 上那些 OpenAlex 搜不到的灰文献/非英文/学位论文，以便不漏关键工作。
2. 作为研究者，我想 GS 抓取跑我自己本地（或我自配的 SERP key），不花 ASCI 的钱、不被 ASCI 服务端代抓，以便服务可持续、隐私可控。
3. 作为研究者，我想就算 GS 抓取被反爬挡住，也至少能一键直达 GS 网页，以便永远有兜底路径。

## Implementation Decisions

- **前置依赖 = 0.4 GS 探索结论**（GS-E1~E4 过阈口径，见 0.4 PRD「前置探索」块）；不达标则按降级档落地，不阻塞 0.5 其余 Epic。
- 定位为 ADR-013「按需现抓 + 外链不落库」的扩展，无新增合规面；结果带回链、不进语料缓存。
- 接现有 lit-search 能力包：GS 作为一个新源接入归一化源层（现 8 个 API 源 → +1 无 API 源），与 OpenAlex / 智能检索互补非替代。

## 验收

- 检索 Agent 能经 L1（user-local）直接拿到 GS 结果，带回链、不落 Corpus（端到端走查）。
- fallback 链就位：L1 失败可降级 L2，全挂时 L3 永远在；ASCI 服务端永不自抓（审计调用链）。
- GS 结果永不进 Corpus（审计语料无 GS 抓取内容）。

## Out of Scope

- 无 API 源扩类（ResearchGate / CNKI / 万方 / 出版商页）→ 0.6/V1（以 GS 实战为门）。
- GS 全文落库 / 缓存再分发 → 永不做（许可红线）。
- 需求驱动语料填充（ADR-014 D4–D6 写侧懒填）→ 本 Epic 不含，归独立块（ADR-014 承载缺口的另一半，待补）。
