## 一、背景

### 触发

0.2 §三-2 V6a 要求：

> 侧边栏"笔记"入口可见,展示当前全部 Note 列表（支持搜索）

这是 0.2 必做项。但用户硬规则（memory `feedback_left_nav_adr.md`）：**LeftSidebar 顶部菜单 / 主进程 menu / tray 加条目前必须先写 ADR**。本 ADR 履行该前置。

> **术语澄清**：memory 原文用"顶部菜单",本 ADR 后文统一改称 "**LeftSidebar 主菜单区**" 以避免与 macOS 系统菜单栏混淆。指代同一对象：`LeftSidebar.tsx:427-460` 中项目切换器下方、会话列表上方的 `SidebarMenuItem` 组（当前 4 项：搜索 / 配置 / 文献库 / 新建任务）。

### 当前 LeftSidebar 入口结构

```
主菜单区（顺序）：
  搜索       (Search dialog, 不切 activeView)
  配置       (打开 Settings → channels tab)
  文献库     (activeView = 'library', Zotero 三栏)
  新建任务   (open new agent session)
```

`activeViewAtom` 当前仅两态：`'conversations' | 'library'`。新增笔记列表视图需要扩展。

### 0.3 / 0.4 阶段的并行变化

| 来源 | 变化 | 对本 ADR 的影响 |
|------|------|----------------|
| 0.3 §三-C.2 | 新建左侧 "配置" 入口,内含 Skill 板块 + 能力包板块 | 出现**另一个**左侧二级入口,需要与"笔记"入口在心智上严格区分（Agent 能力 vs 科研对象） |
| 0.3 §三-C.3 | Settings 弹窗"配置"tab 删除,内容下沉到左侧"配置"页 | 不影响笔记入口（笔记从来不在 Settings 里） |
| 0.4 §三-D | 默认页改造(中心对话框 + 总控 Agent),原"新建任务"入口被消解 | LeftSidebar 主菜单区整体可能收缩,笔记入口需考虑 0.4 后是否仍保留为主菜单区项 |

### 未来全局对象列表的扩展位

0.2 共有 5 核心对象：Paper / EvidenceRef / Note / EvidenceSet / CitationRelation。除 Paper 已在文献库,其余四个之中：

- **Note**：本 ADR 的对象
- **EvidenceSet**：0.2 §三-2 V6 要求"在证据集中可检索关联的 Note",意味着 EvidenceSet 也需要详情入口,未来可能需要"证据集"全局列表
- **CitationRelation**：0.2 §三-1 V2/V2a/V2b 已在 Paper 详情双向展示,可能不需要独立全局视图
- **EvidenceRef**：天然嵌入综述/Paper 视图,不需要独立入口

**这意味着 LeftSidebar 笔记入口的同级位置,未来可能继续扩展（如"证据集"入口）**——本 ADR 不仅决策"加一个笔记入口",还要决策这一类入口的**命名空间与扩展策略**。

### 项目级硬约束

- CLAUDE.md §2 状态规则：Jotai 统一管,不引入新全局状态库 → 走 `activeViewAtom` 扩展
- CLAUDE.md §5 IPC 约定：本 ADR 不涉及 IPC（笔记数据本地优先,Note 存储后端由 ADR-001 决策,本 ADR 只决策入口位置）
- 0.3 §三-C.0 "系统底座 vs Agent 生态"二分原则：Settings 弹窗 = 跨场景共享资源/凭据;左侧"配置"页 = Skill + 能力包;**两者都不是科研对象**——笔记入口属于第三类心智("科研对象",对象的 CRUD 视图)

## 二、决策维度

| 维度 | 关键问题 |
|------|---------|
| **心智分类** | 笔记是和 "文献库" 同级（科研对象视图）还是和 "配置" 同级（管理面板）？ |
| **未来扩展** | 当 0.2 后期 / 0.3 引入 "证据集" 等全局视图时,是新开顶级入口还是聚合到 "知识库" 容器 |
| **0.4 兼容** | 0.4 默认页改造后,主菜单区结构若收缩,笔记入口如何过渡 |
| **路由 / 状态** | `activeViewAtom` 扩展 vs 引入独立路由系统 vs 在 Library 内开子 tab |
| **折叠态** | LeftSidebar 折叠时图标布局如何承载笔记入口 |
| **空状态可见性** | 用户尚未写任何笔记时,入口是否仍显眼（影响 0.3 §七 L2 激活路径） |
| **跟 0.3 "配置"页的视觉差异** | 用户能否在 30s 内分清两个左侧二级入口的心智差异（0.2 §三-4 X1.2 要求验证） |

## 三、候选方案

### 方案 A：主菜单区新增独立"笔记"入口（与文献库平级）

```
主菜单区（新顺序）:
  搜索
  配置
  文献库
  笔记 ← 新增
  新建任务
```

- `activeViewAtom` 扩展为 `'conversations' | 'library' | 'notes'`
- 新建 `NotesView.tsx`：三栏布局 = 左侧过滤侧栏（按 Paper / kind / hypothesisStatus 过滤）+ 中栏笔记列表（搜索框 + 列表项）+ 右栏 Note 详情或预览
- 复用 #4 NoteDetailDialog 的视图层（可能改为非弹层形式嵌入右栏）
- 折叠态：保留 lucide `NotebookPen` 图标在垂直图标列

**优点**：
- 心智清晰：与"文献库"同属"科研对象"层,用户期望"笔记"独立可达
- 落实 0.2 §零 Agent 主导原则的兜底通道（用户全局查看所有手动写的笔记 / 假设）
- 0.3 §七 L2 / L3 激活路径需要笔记有显眼入口（写了第一条笔记后用户能在主导航里找到它）
- 与 0.3 §三-C 的"配置"页定位区别明显:"配置"是 Agent 能力,"笔记"是研究对象

**缺点**：
- 主菜单区从 4 项增到 5 项,折叠态图标列开始拥挤
- 当 EvidenceSet 全局视图也加入时,菜单会变 6 项 → 必须再决策（见后续"扩展策略"）
- `NotesView` 是新页面,工作量比"嵌在 Library 里"大

### 方案 B：嵌入 Library 视图,加 sub-tab 切换

不动 LeftSidebar 主菜单区。在现有的 Library 视图里加 sub-tab：

```
文献库
  └─ [论文][笔记][假设]  ← Library 内部 tab
```

- 不扩展 `activeViewAtom`
- LibraryView 顶部加 tab bar,切换"论文 / 笔记 / 假设"
- "笔记"tab 渲染笔记列表 + 搜索

**优点**：
- 改动面最小,不动左侧栏入口结构
- 不冲击 0.4 默认页改造（主菜单区保持现状）
- "笔记跟着论文走"的隐喻自然（笔记总是依附于 Paper / EvidenceSet）

**缺点**：
- 心智耦合：用户找笔记时心智路径是"文献库 → 笔记"而不是直接"笔记",多一层
- "文献库"当前是 Zotero 三栏视图,加 sub-tab 会重写 LibraryView,改动其实不小
- 0.3 §七 L2 引导（"对这段有想法?写下来"）→ L3（"看看哪些值得保留"）需要笔记有显眼入口,Library 内部 tab 不够显
- 假设跟着 hypothesis kind 也是笔记,Library 标"假设"sub-tab 会让用户以为是独立类对象
- 不利于未来 EvidenceSet 全局视图扩展（"证据集"是否也塞进 Library 内 tab？过载）

### 方案 C：引入"科研对象"二级容器,主菜单区加单一入口"知识库"

```
主菜单区：
  搜索
  配置
  知识库 ← 新增（容器入口）
  文献库
  新建任务

知识库内部（一进入显示侧栏）:
  └─ 笔记
  └─ 证据集（0.2 后期）
  └─ 假设（0.2 后期 hypothesis 子集）
```

- 一个顶级入口"知识库",底下挂多个科研对象子视图
- "文献库" 保留独立顶级入口（因为 Zotero 工具属性强,跟"知识库"的对象元数据是两个体系）

**优点**：
- 主菜单区不会随每个新对象类型不断加项
- 未来 EvidenceSet / CitationRelation 全局视图可直接挂入"知识库"
- 与 0.3 §三-C "配置" 页结构呼应（"配置"也是容器入口,内含 Skill / 能力包两板块）

**缺点**：
- 0.2 阶段只有"笔记"一个子项,容器结构"过早抽象"
- 用户 mental model 不熟悉:"知识库" vs "文献库" 区分需教育成本（X1.2 类似验证项可能跑不通）
- 命名挑战:"知识库" / "对象库" / "我的科研" 都不够直观
- 增加一次点击深度

### 方案 D：不加左侧栏入口,仅在 Settings 数据导出 + Paper 详情侧栏暴露

- 用户全局看笔记只能从设置 → 数据 → 导出 JSON 自己看
- 工作时通过 Paper / EvidenceSet 详情看笔记

**优点**：
- 零侧栏改动

**缺点**：
- **直接违背 V6a 必做项**("侧边栏笔记入口可见"是 0.2 必做)
- 排除

---

## 四、已排除方案

- **D**：违背 V6a 必做要求,直接排除
- **E：把笔记入口加到"配置"页（0.3 §三-C 引入的新左侧入口）**——配置页定义为 "Skill / 能力包 的管理",和"笔记"对象 CRUD 性质不同,会破坏 0.3 §三-C.0 的"系统底座 vs Agent 生态"二分原则
- **F：用 Command Palette（⌘K）暴露笔记入口替代左侧栏**——违背 V6a "侧边栏笔记入口可见" 的字面要求,且 Command Palette 0.2 阶段不存在

## 五、决策

**采纳方案 A**：在 LeftSidebar 主菜单区加独立"笔记"入口,与文献库平级（顺序：搜索 / 配置 / 文献库 / **笔记** / 新建任务）。

拍板人:lexa (Alex),2026-05-18 签字。

理由：

1. **V6a 字面要求**：spec 明确说"侧边栏笔记入口",方案 A 最直接
2. **激活路径需要显眼**：0.3 §七 L2 / L3 引导依赖"用户写完笔记后能在主导航里找到它",方案 B 的 sub-tab 隐藏度过高
3. **0.2 阶段对象数量可控**：当前仅"笔记"一个全局视图候选,容器抽象（方案 C）过早
4. **未来扩展有兜底**：若 0.3 后期需要"证据集"独立入口,届时若菜单变 6 项再考虑是否升级为方案 C 的容器结构（届时已有 X1.2 类似的用户验证数据支撑决策）
5. **0.4 兼容**：0.4 默认页改造主要影响"新建任务"入口,笔记入口可保留为科研对象侧栏项

### 扩展策略

**当左侧栏主菜单区达到 ≥ 6 项时**,触发"是否升级为容器结构"评估。判据：
- 同心智层（科研对象类）入口 ≥ 3 → 升级（笔记 + 证据集 + 引用图谱 全局视图）
- 同心智层入口 ≤ 2 → 维持平铺

## 六、后果

### 共同后果（任一方案）

- `activeViewAtom` 扩展（A 直接加 `'notes'`;B 加内部 sub-tab state）
- 新建 `NotesView.tsx`（A) 或扩展 `LibraryView.tsx`（B）
- i18n 新增 nav / sidebar ns 下"笔记"入口文案,zh + en 同步
- 折叠态布局需更新（A：垂直图标列加 NotebookPen 图标；B：不变）
- `apps/electron/package.json` patch 递增

### 方案 A 额外后果

- LeftSidebar 主菜单区从 4 项变 5 项,需视觉验证：折叠态图标垂直堆叠是否仍能落在视觉舒适区
- `NotesView.tsx` 三栏布局需评估：左过滤栏 / 中列表 / 右详情 → 详情区是用现有 NoteDetailDialog 嵌入还是改写为非弹层组件
- 跨 Paper 反查 Note 性能（V6e: 100+ Note 时响应时间无关）→ 卡 ADR-001 存储后端选型；UI 可先用 mock 数据原型

### 方案 B 额外后果

- LibraryView 重写为带 tab bar 的容器,需评估 Zotero 三栏布局是否仍适配
- 用户从 Library 切到笔记 tab 时,左侧 collection tree 是否仍显示需要决策（Zotero collection 跟笔记无关）
- 0.3 §七 L2/L3 引导触发位置需调整（从"全局笔记入口"改为"Library → 笔记 tab"）

### 风险

| 风险 | 缓解 |
|------|------|
| 主菜单区 5 项后用户对"配置（Settings）vs 配置页（0.3 §三-C 左侧入口）vs 笔记"心智混乱 | 0.2 §三-4 X1.2 用户验证项需要在测试中加入笔记入口,验证三个左侧二级入口的心智识别度 |
| 笔记入口为空状态时是否仍显示 | UI 走查：空状态显示引导文案 + 直接跳"去文献库选论文写第一条"按钮,而不是隐藏入口 |
| 0.4 默认页改造后笔记入口位置变更 | 0.4 启动时本 ADR 状态从 Accepted 转为 Superseded by ADR-XXX(默认页布局相关) |
| ADR-001 未签,V6e 性能要求跑不通 | 笔记入口 UI 可先用 mock 数据原型完工,V6e 真实查询性能等 ADR-001 落地后再连 |

1. 在 worktree 中新建 `NotesView.tsx`（或 LibraryView sub-tab）+ atoms

4. i18n 双语 key 落齐 + key-parity 测试通过
