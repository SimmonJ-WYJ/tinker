# Tinker 产品方向

## 一句话定位

Tinker 是面向跨模型创作与开发任务的桌面 Agent：让用户在同一个任务中组合使用不同渠道提供的模型和工具，保留上下文与产物，明确选择与费用，减少在多个产品间切换的负担。

SiliconFission 是优先验证的接入渠道，不是已经完成的集成。降低总成本是目标和待验证假设，不承诺所有任务更便宜，也不承诺替代所有订阅。

## 用户与问题

首批候选用户是已经使用多种 AI 产品、有自己的 API 渠道、需要同时完成文字、代码和视觉任务的个人创作者、设计师与独立开发者。该画像是规划假设，尚未通过访谈验证；首批内测人群与主任务由产品负责人决定。

他们的任务是把一个想法做成可用成果。当前痛点包括：不同产品分别订阅、能力分散、上下文反复搬运、产物版本难追踪、调用费用与失败成本难判断。Tinker 的价值应通过完整任务完成情况证明，不能仅以可选择模型数量衡量。

## 产品原则与边界

- 同一任务允许不同步骤使用不同模型；渠道是访问与计费路径，模型是具体推理/生成服务，工具是执行能力，不能混为一个开关。
- 用户能看到实际渠道、模型、能力与使用限制，手动选择优先。自动选择属于后续阶段，必须可解释、可覆盖、受预算约束。
- 默认保留上下文、草稿、失败进度和产物来源；切换不应让用户重新开始。发送到另一渠道前，应说明会转交哪些内容。
- API 支持什么就提供什么。模型 API 不自动包含第三方产品的设计画布、编辑器、插件、工作流或订阅权益。
- 不把 GPT 图像、Claude 相关设计体验、视频、世界模型和游戏开发视为已接通的一组能力。具体模型名、版本、接口与授权均按渠道证据验证。
- 本地桌面体验优先；未来允许本地与云端协作，但本地部署、多 Agent 和云端同步不进入首个可用版本。
- 尊重依赖、素材及上游条款；不复制旧 ASCI 代码或资产，不移除署名，不宣称重新编写自动获得全部权利。

## 核心流程

用户建立任务并说明目标 → 选择可用渠道与模型 → 查看数据发送范围与费用信息 → Agent 提出步骤 → 用户授权必要操作 → 执行并显示进度 → 保存文本、代码、图片等关联产物 → 失败时从明确步骤恢复 → 用户检查并导出成果。

首条候选跨能力验证任务：**在一个任务中生成一个网页方案及配图，并产出可预览的本地页面**。文本/代码模型负责方案与页面，经过验证的图像接口生成配图；如果执行涉及文件写入、运行命令或向外传输内容，遵守 PRD 权限规则。此任务是建议，尚未选定，也尚未实现。若渠道没有可用图像 API，必须先调整试点任务，不得用演示图冒充完成。

## 阶段目标

| 阶段 | 目标 | 完成门槛 |
|---|---|---|
| 当前骨架 | 验证状态隔离与开发结构 | 仅作为演示底座，不算可用模型产品 |
| P0 | 可靠的真实模型对话与渠道管理 | 配置、流式、取消、保存、失败恢复、基本费用/隐私提示均验收 |
| P1 | 一个同任务跨能力 Agent 闭环 | 至少两个经验证能力协作，产物可追溯，权限和恢复可用 |
| P2 | 图像生成与连续编辑 | 引用、版本、编辑能力与费用逐项验证；失败不覆盖旧图 |
| 后续 | 视频、世界模型、游戏工作流、本地/云端协作与自动路由 | 依据接口、授权、成本及内测反馈分别立项 |

P0 是必要底座，P1 才首次检验核心差异。若 P1 已包含首次生图，P2 重点是连续编辑和稳定体验，不重复定义首次接入。

## 如何判断值得继续

内测记录每个任务的完成率、人工接管次数、工具切换次数、总耗时、调用次数、失败重试次数与实际费用。与用户原有流程比较时，使用相同任务和相近质量要求，说明 API 与订阅的计费口径差异。首轮先采集基线，再决定目标阈值；在阈值未批准前不对外宣称节省比例。
