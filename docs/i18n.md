# i18n 规范

> ASCI 项目所有面向用户 UI 文案的国际化（i18n）权威规则。CLAUDE.md §2 与 §7.4 引用本文件。
> 修改本文件前需征得用户允许（与 CLAUDE.md / README.md 同级硬约束）。

---

## 1. 速览（一句话原则）

任何面向用户 UI 文案必须走 `useT(ns)` / `t(key)`；en + zh 同步增减 key；由 `key-parity.test.ts` 守门。违反任一条会导致漏翻 / 半翻 / Agent 选择路径被翻译干扰。

---

## 2. 体系地图（"东西在哪"）

### 2.1 框架与入口
- `react-i18next` + 自家 `i18n.ts` 单例
- 业务侧**只能**通过 `hooks/useT.ts` 与 `components/common/Trans.tsx` 取 t / Trans

### 2.2 资源布局
- 命名空间清单：`common / settings / nav / library / conversation / onboarding / skills / errors / chrome`
- 每个 ns 对应 `apps/electron/src/renderer/locales/<lang>/<ns>.json`
- 大型 ns 拆段位置：`settings/` / `conversation/` / `library/` 已按 `locales/<lang>/<ns>/<section>.json` + `locales/<lang>/<ns>.ts` 聚合的模式拆分

### 2.3 主进程 i18n
- 入口：`apps/electron/src/main/lib/i18n-main.ts`，不依赖 i18next
- 复用 renderer 端的 `chrome.json / errors.json / common.json` 资源
- 靠 `setLanguage` + `onLanguageChange` 驱动 menu / tray / 主进程对话框
- menu / tray / 主进程对话框文案走 `lib/i18n-main.ts` 的 `t()`

### 2.4 语言事实源
- `~/.asci/settings.json` 的 `language` 字段为唯一真相
- renderer `updateLanguage()` 写设置后调用 `i18n.changeLanguage`
- main 在 `settings:update` 处理器里同步 `setLanguage` —— **禁止绕过此处理器另开 IPC**，否则双源失同步

### 2.5 类型层
- 类型补全入口：`apps/electron/src/renderer/lib/i18n-types.d.ts` 把 en 资源注入 `react-i18next` 的 `CustomTypeOptions.resources`
- 新增 ns 时**必须**同时更新 `locales/index.ts` 的 `defaultResources` / `I18N_NAMESPACES` 与 `lib/i18n-types.d.ts` 的 `CustomTypeOptions.resources`，否则 `t('newns.x')` 丢失类型补全

### 2.6 守门测试
- `apps/electron/src/renderer/locales/key-parity.test.ts` 逐 ns 校验 en / zh key 严格相等
- 提交前自跑 `bun test` 必通过

## 3. 硬约束

违反任一条会导致漏翻 / 半翻 / Agent 选择路径被翻译干扰，必须严格遵守。

### 3.1 禁止 inline 硬编码（覆盖范围）

所有最终渲染到用户的字符串字面量都要走 `useT(ns)` / `t(key)`：

- **JSX 文本子节点**：toast / button label / dialog title / 错误提示等
- **变量声明**：`const` / `let` / `var` 中持有面向用户文案的字符串字面量（如 `const tip = '保存成功'`），无论是否当场渲染
- **HTML / JSX 属性**：`alt` / `title` / `aria-label` / `aria-description` / `aria-*` / `placeholder` / `rel` / `data-tooltip` 等任何会被屏幕阅读器或浏览器展示给用户的属性
- **React 组件 props**：渲染为文本的 props（`label` / `description` / `tooltip` / `placeholder` / `emptyText` / `confirmText` / `cancelText` 等）
- **条件渲染分支**：`isError ? '失败' : '成功'` 三元、`flag && '...'` 短路、`switch` 返回字符串 —— **每一个分支都要 i18n**，不能只翻默认分支

**不在范围（保留原样，禁止动 i18n）**：

- 代码注释：行内 `//`、块 `/* */`、JSDoc
- 调试与日志输出：`console.log` / `console.warn` / `console.error` / `console.debug`，`logger.*`，主进程 / 渲染进程文件日志
- 仅给开发者看的内部 Error：`throw new Error('internal: …')`、传给开发者控制台的 message（**不会**渲染到 UI 的那部分）
- Agent / Skill 输出的 markdown 正文、由 LLM 生成的字符串、用户自建 Agent / Skill 的 prompt 文本
- **dev-only 代码**：被 `useIsDevMode()` / `getIsDevMode()` / `<DevOnly>`（`@/lib/dev-mode`）门控的功能 / 逻辑 / UI —— 有效 dev 模式（Vite dev server，**或**「关于」页连点版本号解锁的 Debug 开关）下才可见，普通终端用户默认不可达，故其内文案 **无需** i18n，直接硬编码即可（含 debug 按钮、reparse 测试按钮等开发探针）。注意：自 Debug 开关引入后，这些代码**不再被生产构建 tree-shaking 剥离**（改为运行期 atom 门控、打进产物），但仍只在用户主动开启 Debug 后才显示，i18n 豁免依旧成立。`key-parity.test.ts` 只校验真正落进 `locales/` 的 key，dev-only 文案本就不进资源文件，不受守门约束

### 3.2 en + zh 同步

- 新增 / 删除 / 重命名 key 必须两侧同时修改
- CI 由 `key-parity.test.ts` 守门，提交前自跑 `bun test` 必通过

### 3.3 命名空间边界

- 业务侧 t 调用通过 `useT('<ns>')` 限定到一个 ns
- 跨 ns 文案各取自己的 t（避免类型补全失效）

### 3.4 大型 ns 必须拆分

单个命名空间的 JSON 超过 ~100 行 **或** 顶层包含 4+ 个独立功能段时，必须按 `settings/` / `conversation/` / `library/` 的现有模式拆为 `<ns>/<section>.json` + `<ns>.ts` 聚合：

- 每段一个 JSON，对应 UI 子域（如 `settings/agent.json`、`conversation/permission.json`）
- `<ns>.ts` 用 `...spread` 合并所有段，保持单一 ns 命名空间表象
- en + zh 两侧同步拆分，目录结构完全镜像，`key-parity.test.ts` 仍逐 ns 严格相等
- `locales/index.ts` 与 `lib/i18n-types.d.ts` 引用聚合后的 `<ns>` 资源，业务侧 `useT('<ns>')` 调用方式不变

### 3.5 Skill `nameI18n` 是 UI-only

- `SkillMeta.name` / `description` 必须保持英文唯一
- Agent 注入路径只读 `name` / `slug`，**不得读 `nameI18n`**，否则模型选择 skill 的 prompt 会随语言抖动

### 3.6 `packages/` 解耦

`packages/shared` / `packages/core` / `packages/ui` 等共享库内的函数与组件 **不允许** `import` `react-i18next` / `i18next` / 任何 `useT`，必须通过 param 或 prop 接收已翻译好的字符串。

- **约束理由**：packages 是 framework-agnostic 的库代码，被 apps/electron 与潜在其他宿主复用；耦合 i18n singleton 会污染下游、阻碍单测，也违反 packages 的"零业务依赖"边界
- **现有范例**：`packages/ui/src/code-block/CodeBlock.tsx` 用 `copyLabel?` / `copiedLabel?` props；调用方在 `apps/electron/src/renderer/components/ai-elements/message.tsx` 里 `useT('common')` 取 t 后包成 `{ copyLabel: t('copy'), copiedLabel: t('copied') }` 传入
- **反例**：在 `packages/` 内 `import { useTranslation } from 'react-i18next'` 或 `import { useT } from '...'`

### 3.7 测试文件禁用 i18n

- `*.test.ts(x)` / `*.spec.ts(x)` 内 **禁止** `i18n.changeLanguage(...)` / `I18nextProvider` 包裹
- 断言走原始英文 key、固定常量或 mock 出的 t（如 `t: (k: string) => k`）
- **约束理由**：i18n 资源会随翻译迭代而变；断言绑定具体翻译文本会让测试随翻译漂移，破坏 CI 稳定性
- **例外**：`key-parity.test.ts` 这类"测 i18n 资源本身"的元测试不受此约束
- 复合组件测试若涉及 t 调用，优先抽出纯逻辑做单测；非要 render 时，给组件传一个稳定的假 t（如 `t={(k) => k}`）即可

### 3.8 解除 dev 门控时必须回填 i18n

§3.1「不在范围」对 dev-only 文案的 i18n 豁免，**仅因该代码被 dev 门控、普通终端用户默认不可达才成立**。一旦移除门控——删掉 `<DevOnly>` 包裹、或删掉 `useIsDevMode()` / `getIsDevMode()`（`@/lib/dev-mode`）的判断条件，把功能提升为所有用户默认可见的生产 UI——豁免**当场失效**，原先直接硬编码的文案就变成会发给全体用户的裸字符串。

故每次解除 dev 门控时，**必须**把被解放的那段 UI 当成新写的生产文案处理：

- 逐一排查该段内所有面向用户的字符串字面量（JSX 文本、属性、props、条件分支），按 §3.1 全部改走 `useT(ns)` / `t(key)`
- en + zh 两侧同步补齐对应 key（§3.2），确保 `key-parity` 守门通过
- 同时按 [`docs/design.md`](./design.md) §九补做 theme 回填（调色板硬编码 → 语义 token、亮/暗双主题验证）——i18n 与 theme 两项豁免随门控一并失效，需一起回填

⚠️ review checklist：凡 PR 删除了 `<DevOnly>` / `useIsDevMode()` / `getIsDevMode()`，必须连带检查该 diff 是否引入了未 i18n 文案与调色板硬编码。

## 4. 操作清单（碰到 UI 文案时按顺序走）

1. 先在 `apps/electron/src/renderer/locales/<lang>/<ns>/...` 下找 / 加 key，en 与 zh 同步落键
2. 组件里走 `useT(ns)` 引用，跨 ns 各取各的 t
3. 新增 ns？同步更新 `locales/index.ts` 与 `lib/i18n-types.d.ts`
4. 大型 ns 触发 §3.4 拆分阈值？按 `<ns>/<section>.json` + `<ns>.ts` 聚合
5. `bun test` 跑 `key-parity.test.ts` 必通过
6. UI 改动在 `bun run dev` 中切 zh ↔ en 各走一遍，确认无 raw key 与漏翻
