# i18n Rules

> Authoritative internationalization (i18n) rules for all user-facing UI copy in ASCI. Referenced by CLAUDE.md §2 and §7.4.
> User permission is required before modifying this file (the same hard constraint as CLAUDE.md / README.md).

---

<a id="1-速览一句话原则"></a>

## 1. Quick Reference (One-Sentence Principle)

All user-facing UI copy must use `useT(ns)` / `t(key)`; add/remove keys in en + zh together, guarded by `key-parity.test.ts`. Violations cause missing/partial translations or let translation interfere with Agent selection paths.

---

<a id="2-体系地图东西在哪"></a>

## 2. System Map (“Where Things Live”)

<a id="21-框架与入口"></a>

### 2.1 Framework and Entry Points
- `react-i18next` + our `i18n.ts` singleton
- Business code **must obtain** t / Trans only through `hooks/useT.ts` and `components/common/Trans.tsx`

<a id="22-资源布局"></a>

### 2.2 Resource Layout
- Namespace list: `common / settings / nav / library / conversation / onboarding / skills / errors / chrome`
- Each ns maps to `apps/electron/src/renderer/locales/<lang>/<ns>.json`
- Large namespace splits: `settings/` / `conversation/` / `library/` already use `locales/<lang>/<ns>/<section>.json` + `locales/<lang>/<ns>.ts` aggregation

<a id="23-主进程-i18n"></a>

### 2.3 Main-Process i18n
- Entry: `apps/electron/src/main/lib/i18n-main.ts`, independent of i18next
- Reuses renderer `chrome.json / errors.json / common.json` resources
- `setLanguage` + `onLanguageChange` drive menus / tray / main-process dialogs
- Menu / tray / main-process dialog copy uses `t()` from `lib/i18n-main.ts`

<a id="24-语言事实源"></a>

### 2.4 Language Source of Truth
- The `language` field in `~/.asci/settings.json` is the sole source of truth
- Renderer `updateLanguage()` writes settings before calling `i18n.changeLanguage`
- Main synchronizes `setLanguage` in the `settings:update` handler: **never bypass this handler with another IPC**, or the two sources become unsynchronized

<a id="25-类型层"></a>

### 2.5 Type Layer
- Type completion entry: `apps/electron/src/renderer/lib/i18n-types.d.ts` injects en resources into `react-i18next`'s `CustomTypeOptions.resources`
- Adding an ns **must** update `defaultResources` / `I18N_NAMESPACES` in `locales/index.ts` and `CustomTypeOptions.resources` in `lib/i18n-types.d.ts` together, or `t('newns.x')` loses type completion

<a id="26-守门测试"></a>

### 2.6 Guard Tests
- `apps/electron/src/renderer/locales/key-parity.test.ts` verifies exact en / zh key equality per ns
- Local `bun test` must pass before committing

<a id="3-硬约束"></a>

## 3. Hard Constraints

Violations cause missing/partial translations or let translation interfere with Agent selection paths; follow every rule strictly.

<a id="31-禁止-inline-硬编码覆盖范围"></a>

### 3.1 No Inline Hardcoding (Coverage)

Every string literal ultimately rendered to users must use `useT(ns)` / `t(key)`:

- **JSX text children**: toasts / button labels / dialog titles / error notices, etc.
- **Variable declarations**: user-facing string literals held in `const` / `let` / `var` (such as `const tip = '保存成功'`, meaning “Saved successfully”), whether rendered immediately or not
- **HTML / JSX attributes**: `alt` / `title` / `aria-label` / `aria-description` / `aria-*` / `placeholder` / `rel` / `data-tooltip`, or any attribute shown to users by screen readers or browsers
- **React component props**: props rendered as text (`label` / `description` / `tooltip` / `placeholder` / `emptyText` / `confirmText` / `cancelText`, etc.)
- **Conditional rendering branches**: `isError ? '失败' : '成功'` (failure/success) ternaries, `flag && '...'` short circuits, and `switch` string returns: **every branch needs i18n**, not just the default branch

**Out of scope (retain unchanged; do not apply i18n)**:

- Code comments: inline `//`, block `/* */`, JSDoc
- Debug/log output: `console.log` / `console.warn` / `console.error` / `console.debug`, `logger.*`, main/renderer file logs
- Developer-only internal Errors: `throw new Error('internal: …')`, messages sent to developer consoles (the portion **never** rendered in UI)
- Markdown bodies from Agent / Skill output, LLM-generated strings, and prompt text in user-created Agents / Skills
- **dev-only code**: features / logic / UI gated by `useIsDevMode()` / `getIsDevMode()` / `<DevOnly>` (`@/lib/dev-mode`) appear only in effective dev mode (Vite dev server **or** the Debug switch unlocked by repeatedly clicking the version on About). Ordinary users cannot reach them by default, so their copy **does not need** i18n and may be hardcoded (including debug buttons, reparse test buttons, and other developer probes). Note: since the Debug switch was introduced, production builds **no longer remove this code through tree-shaking** (it is bundled and gated by runtime atoms), but it still appears only after users explicitly enable Debug, so the exemption remains. `key-parity.test.ts` checks only keys actually in `locales/`; dev-only copy never enters resource files and is outside this guard

<a id="32-en-&#45;zh-同步"></a>

### 3.2 Synchronize en + zh

- Add / delete / rename keys on both sides together
- CI is guarded by `key-parity.test.ts`; local `bun test` must pass before committing

<a id="33-命名空间边界"></a>

### 3.3 Namespace Boundaries

- Business-code t calls use `useT('<ns>')` to restrict themselves to one ns
- Obtain a separate t for each ns when using cross-namespace copy (to preserve type completion)

<a id="34-大型-ns-必须拆分"></a>

### 3.4 Split Large Namespaces

When one namespace JSON exceeds ~100 lines **or** contains 4+ independent top-level feature sections, split it using the existing `settings/` / `conversation/` / `library/` pattern: `<ns>/<section>.json` + `<ns>.ts` aggregation:

- One JSON per section, corresponding to a UI subdomain (e.g. `settings/agent.json`, `conversation/permission.json`)
- `<ns>.ts` merges all sections with `...spread`, preserving the appearance of a single ns
- Split en + zh together with exactly mirrored directories; `key-parity.test.ts` still verifies strict per-ns equality
- `locales/index.ts` and `lib/i18n-types.d.ts` reference aggregated `<ns>` resources; business-side `useT('<ns>')` calls stay unchanged

<a id="35-skill-namei18n-是-ui-only"></a>

### 3.5 Skill `nameI18n` Is UI-Only

- `SkillMeta.name` / `description` must remain English-only
- Agent injection reads only `name` / `slug`, **never `nameI18n`**, or the model's skill-selection prompt changes with UI language

<a id="36-packages-解耦"></a>

### 3.6 Decouple `packages/`

Functions and components in shared libraries such as `packages/shared` / `packages/core` / `packages/ui` **must not** `import` `react-i18next` / `i18next` / any `useT`; receive translated strings through parameters or props.

- **Rationale**: packages are framework-agnostic libraries reused by apps/electron and potential other hosts; coupling an i18n singleton pollutes downstream consumers, obstructs unit tests, and violates the packages' “zero business dependencies” boundary
- **Existing example**: `packages/ui/src/code-block/CodeBlock.tsx` uses `copyLabel?` / `copiedLabel?` props; its caller in `apps/electron/src/renderer/components/ai-elements/message.tsx` obtains t via `useT('common')`, then passes `{ copyLabel: t('copy'), copiedLabel: t('copied') }`
- **Counterexample**: inside `packages/`, using `import { useTranslation } from 'react-i18next'` or `import { useT } from '...'`

<a id="37-测试文件禁用-i18n"></a>

### 3.7 No i18n in Test Files

- In `*.test.ts(x)` / `*.spec.ts(x)`, **never** call `i18n.changeLanguage(...)` or wrap with `I18nextProvider`
- Assertions use original English keys, fixed constants, or mocked t (e.g. `t: (k: string) => k`)
- **Rationale**: i18n resources evolve with translations; assertions tied to specific translated copy drift with translations and destabilize CI
- **Exception**: meta-tests of i18n resources themselves, such as `key-parity.test.ts`, are exempt
- If composite component tests call t, prefer extracting pure logic for unit tests; if rendering is essential, pass a stable fake t (e.g. `t={(k) => k}`)

<a id="38-解除-dev-门控时必须回填-i18n"></a>

### 3.8 Removing Dev Gates Requires i18n Backfill

The §3.1 “Out of scope” exemption for dev-only copy applies **only because the code is dev-gated and unreachable by ordinary users by default**. Removing that gate, such as deleting `<DevOnly>` wrappers or `useIsDevMode()` / `getIsDevMode()` (`@/lib/dev-mode`) conditions to expose a feature to all users as production UI, **immediately voids** the exemption; previously hardcoded copy becomes raw strings delivered to everyone.

Therefore every removal of a dev gate **must** treat the exposed UI as newly written production copy:

- Inspect every user-facing string literal in that section (JSX text, attributes, props, conditional branches) and convert all to `useT(ns)` / `t(key)` under §3.1
- Add corresponding keys to both en + zh (§3.2), ensuring the `key-parity` guard passes
- Also backfill themes under [`docs/design.md`](./design.md) §IX (hardcoded palette → semantic tokens, light/dark validation); both i18n and theme exemptions end with the gate and must be addressed together

⚠️ Review checklist: any PR deleting `<DevOnly>` / `useIsDevMode()` / `getIsDevMode()` must also check whether the diff introduces untranslated copy or hardcoded palette colors.

<a id="4-操作清单碰到-ui-文案时按顺序走"></a>

## 4. Checklist (Follow in Order When Handling UI Copy)

1. Find / add keys under `apps/electron/src/renderer/locales/<lang>/<ns>/...`, adding en and zh together
2. Reference via `useT(ns)` in components; obtain a separate t for each ns
3. New ns? Update `locales/index.ts` and `lib/i18n-types.d.ts` together
4. Large ns reaches §3.4's split threshold? Use `<ns>/<section>.json` + `<ns>.ts` aggregation
5. `bun test` must pass `key-parity.test.ts`
6. In `bun run dev`, exercise UI changes in zh ↔ en and confirm no raw keys or missing translations
